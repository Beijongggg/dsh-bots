## 0. 共识基线（不再讨论的部分）

以下判定经两轮交叉核验，作为本文档的前提：

| 判定 | 证据 |
|---|---|
| 无限自动 ping-pong 物理上不可能 | `handleIncoming` 对 `kind:"mail-response"` 不回路由 |
| 回合级超时已有硬兜底 | `AGENT_TURN_TIMEOUT_MS`(10min)、`RPC_MAX_TIMEOUTS`、自愈上限 |
| send_mail 是 consult 语义（agents-as-tools），无 handoff 对应物 | 异步投递 + 发起方保留回合控制权；常驻进程模型无"活跃槽位"可移交 |
| Chat/Event 分离已由进程边界天然解决 | 每个 bot 独立会话；能进对方上下文的只有邮件正文 |
| 模型异构已有 | 注册表 `modelProvider`/`model` 字段 + `session.selectModel`（index.js:1549） |

**净缺口只有两个半**：① 邮件无线程结构（多跳断链）；② 终止/升级靠劝导且升级是隐式的；半个 = 文档缺 consult 语义说明。

## 1. 提案一：`replyTo` 字段（优先级最高）

### 1.1 动机

- **多跳断链**：A→B 委托、B 转手派 C、C 回 B 时，没有任何字段能把这条链串回 A 的原始请求。
  单跳认亲目前靠文本前缀 `[mail reply from bot "X"]`（index.js:1789），纯散文约定。
- **解锁未来的硬终止护栏**：一旦线程有结构化链接，线程深度变成 host 侧可计算量，
  "hop 上限"才从不可立项变为可立项。当前所有终止手段都是劝导或单点兜底，
  根因是**没有数据结构支撑深度计算**。这是 replyTo 超出"可观测性"的核心价值。

> 【复核批注·价值降调】上述两条动机与 §1.4 的『send_mail = 线程根』声明存在张力，**v1 实际够不到它们**：
> ① 多跳断链——B 用 send_mail 派 C 是**新线程根**、不连回 A，v1 只解决**单跳 A↔B 认亲**，委派跳仍断链；
> ② 硬护栏——replyTo 是**父指针、只连自动回信边**；自动回信乒乓已被 §0 挡死，而真正无界的**委派循环**每次 send_mail 都重置根，深度计数**数不到委派跳**。
> 结论：v1 真实价值 = **用结构化指针替代脆弱的 `[mail reply…]` 文本认亲（单跳）**。上面两条应改标为 **post-v1、以 send_mail 透传线程根（见 Q1）为前提**——否则正是 §1.4 自己警告的"预期跑偏"。
>
> 【评审再批】接受降调，并给 post-v1 前提补上机制依据：§1.4 已确认模型看得到**出向** seq（发信回执 `delivered to c (seq N)`），而委派跳恰在出向可见域内——post-v1 的「send_mail 透传线程根」不是愿望，引用原料已天然躺在 worker 的上下文里（历史发信回执）。反向半边同样成立：**入向** seq 永不可见，故 v1 自动回信边必须 host 接线。两条结论互为印证。

### 1.2 字段设计

```jsonc
// mail-response 自动回信的信封新增一个可选整数：
{ "seq": 7, "from": "b", "text": "...", "at": "...",
  "kind": "mail-response", "replyTo": 5 }
```

**语义绑定（关键决策）**：`replyTo` 指**回信方自己 inbox 里那条触发消息的 seq**。
解析规则：收到来自 bot B 的带 `replyTo: n` 的消息 → 去 `inbox/b/messages.jsonl` 找 `seq === n`。
无需额外命名空间字段，因为自动回信永远应答自己 inbox 里的消息，发送方身份即解析键。

> 【复核批注·选型边界】父指针只承载**单跳自动回信认亲**，**不承载跨委派跳的深度/树计算**。若终极目标是深度护栏或任务树，需要沿 send_mail 透传**线程根 id**（而非父指针）。v1 不受影响，但此边界须随实现写进文档。

### 1.3 实现面（约三处小改）

| 位置 | 改动 |
|---|---|
| `appendMessage`（index.js:434） | 可选参数 `replyTo`：`Number.isInteger(replyTo) && replyTo > 0` 时写入，否则省略字段 |
| `routeReplyToSender`（index.js:1764，投递的 `appendMessage` 调用处） | 投递时传 `replyTo: message.seq`（触发消息在自己 inbox 的 seq，现成在手） |
| `tests/reply-route.test.mjs` | 场景 4 加断言 `routed[0].replyTo === 1`（触发 seq）。【复核更正】**场景 5 无回投可断言**——`mail-response` 在 `routeReplyToSender` 头部（:1761）早退、不产生回信；第二个断言应落**场景 8 自愈路径** `healedRouted[1].replyTo === 5`（触发 seq=5）。【评审再批】认领：场景 5 断言系原稿笔误，更正成立 |

**兼容性**：旧消息无此字段 = 线程根或未知；JSONL 容错解析不受影响；watcher 游标语义无关。

### 1.4 设计原则与边界（批注）

- 【共识】**v1 由 host 接线，零模型配合**。v1 只覆盖自动回信这一种边——恰好它也是唯一确定性的边。
- 【复核更正】原稿『模型上下文里根本看不到 seq 数字』**与代码不符**：`send_mail` 的 render 返回
  `mail delivered to b (seq N)`（index.js:1894），**模型每次发信都拿到对方 inbox 的 seq**。
  v1 不让模型填 replyTo 的真正理由是：该 seq 是**收件方 inbox 作用域**、只对续接同一收件人有意义，
  且让 LLM 跨回合记账线程不可靠——是"作用域 + 可靠性"，**不是"看不见"**。
- 【评审再批】接受，并把可见性切成两半钉死：**出向 seq 可见**（render 回执）、**入向 seq 永不可见**（inbox 消息从不带 seq 进上下文）。§1.1 的 post-v1 可行性挂在前一半上，本条 v1 必要性挂在后一半上，见 §1.1 评审再批。
- 【评审再批·锚点修正】复核方提议以 `appendMessage 信封 { from, text }`（:1928）作入向不可见的证据——**锚点错位**：那是 send_mail 出向投递侧的调用形态；`appendMessage` 落盘信封实为 `{seq, from, text, at[, kind]}`（index.js:441-442），seq 就在里面。入向不可见的**直接证据**是消费路径：`handleIncoming` 拼 `promptText` 只取 `前缀 + message.text`（index.js:1787-1790），原样透传进 `runNativeAgentTurn`（:1793）——seq 从未进入任何模型上下文。
- 【批注】send_mail 新任务和用户消息是**线程根**（无 replyTo）。线程 = 以种子邮件为根、
  沿自动回信边生长的生成树。这个覆盖面声明必须随实现写进文档，防止预期跑偏。
- 【待议 Q1】够不够：如果未来出现"worker 显式续接旧任务"的需求，要不要开放 send_mail
  的可选 replyTo 参数？**v1 明确不做**（理由见上：作用域 + 记账可靠性，**非**『看不见 seq』）。
  【复核意见】既然 seq 已对模型可见，未来若要开放续接，更自然的做法是**沿 send_mail 透传线程根 id**，
  而非『给模型看线程摘要』。
- 【待议 Q2】前端 v1 不动（讨论组已折叠展示）。任务树视图留作后续独立提案。

## 2. 提案二：协作条款 v2（落在现成 section 上，零基建）

### 2.1 现状（registerTeamPromptSection 的三条协议）

1. 怎么写：to 填 id/名字，text 写完整任务；
2. 发完不等：回信自动开启下一回合；
3. 判断标准：适合队友的转交，适合亲自做的自己做。

复审确认：**无任何回合计数概念**。

### 2.2 新增文案草案（接在三条之后）

> 4. 委派必须自包含：对方只能看到你的正文，请把任务、必要背景、期望产出和验收标准一次写全，不要指望对方追问。
> 5. 回信只交结论：完成委托后，回复写清「做了什么 / 如何验证的 / 已知边界或残留风险」，不要复述中间过程。
> 6. 升级是一等动作：同一任务与队友往返三轮仍未收敛，或你判断事情超出自己的角色边界与权限，立即显式升级——以 `[ESCALATE]` 开头发邮件给领队，正文用中文写明卡在哪里、已经试过什么、需要谁拍板。不要把升级混在正常进度汇报里。（Q4 已决·折中案）

> 【复核批注】三条文案认同；第 6 条把升级做成显式一等动作、以及 §2.3 的可见性警告都对。
> 唯「[升级]」前缀与 Q4 联动，见 §2.3 复核反方意见。

### 2.3 批注与预期管理

- 【共识】这三条是**劝导，不是强制**。没有回合计数器，"三轮"由 LLM 自行体感；
  真正的硬兜底仍是既有 ping-pong blocker + 回合超时。文案价值在于软化收敛体验、
  把升级从隐式错误跌落（`[bot error]` 混在 outbox 里）变成显式声明的状态转移——
  这是 LangGraph `Command.PARENT` 的教训：子层向上走必须是一次显式声明。
- 【批注·可见性警告】worker→worker 的往来默认折叠在讨论组里。若升级发生在两个
  worker 之间，**恰恰是最需要用户看见的消息最可能被折叠藏住**。缓解顺序：
  v1 条款规定"升级发给领队"（领队在主对话线上，用户必然经过）；后续可做
  host/前端识别 `[升级]` 前缀做前台提醒。
- 【待议 Q3】升级收件人约定：统一发领队是否合理？lead 自己的"升级"就是直接在
  与用户的对话里说（它本来就在主线上）——这点要不要也写进去？
  【复核意见】赞成"都入"：worker 升级发领队；lead 升级=直接在主对话说，避免 lead 也去 `[升级]` 自己。
- 【待议 Q4】前缀定「[升级]」（半角括号，与既有 [mail…]/[bot error] 家族一致、可 grep）。
  若嫌中英混杂可换 `[ESCALATE]`，但中文界面下前者对模型的语用拉力更强。
  【复核意见·反方】**倾向 `[ESCALATE]`**。"[升级] 语用拉力更强"成立的前提是 v1 纯文本、只给模型和人看；
  但上一条已明确"后续 host/前端识别前缀做提醒"——一旦要做**程序化检测**，ASCII 稳定 token 比 CJK token
  在正则/编码上更稳。既然检测已写进规划，不如现在就定 `[ESCALATE]`；若要兼顾中文拉力，可折中为**正文中文措辞 + 机器锚点 `[ESCALATE]`**。
  【评审再批】倾向折中案。补一条无论选哪个都成立的告警：既有前缀家族（[mail…]/[bot error]）均为 host 生成的精确串，升级前缀却是**模型生成的**——逐字复现无保证，检测正则须容忍大小写与行内位置变体。
- 【已决 Q4·检测规格】正则 `/\[ESCALATE\]|\[升级\]/i`：对整段 text 匹配、不锚定行首、容忍前后空白与全角括号变体（采纳自复核方意见）。**v1 不写任何检测代码**——条款纯劝导，本规格是前瞻契约，防止未来实现时遗忘容错。

## 5. 明确不做（防复议）

- 编排引擎 / 拓扑预设 —— 领队角色文本就是组织架构，MetaGPT 证明 SOP 可活在提示词里；

- handoff 半边 —— 无活跃槽位，伪需求；
- Chat/Event 再分离 —— 进程边界已是物理级实现；
- 向量记忆 / RAG 机械 —— markdown + 文件检索在此规模完胜。
